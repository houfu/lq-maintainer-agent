# Proposal — v0.7.2 candidates: label support, breaking-change detection, a release narrative (PROPOSED 2026-08-05; open questions ruled 2026-08-05)

Three features, proposed together because they compose: the
breaking-change detector produces a signal, label support publishes
that signal (among others) onto the GitHub item, and the release
narrative consumes both when the maintainer cuts a release. Adoption
would be design delta v0.7.2 over v0.7.1; implementation would be the
next plugin minor (v0.5.0 — two new skills and a new check script are
not a patch).

**What this proposal does not touch:** every constraint in v0.7 §10
holds verbatim. A human decides every write; labels and release notes
are drafts behind per-write permission prompts like every other write;
nothing here adds a write command to any `allowed-tools` block; the
agent still never executes contributed code, and no signal introduced
here can move an item to a *lighter* lane, category, or tier (L-04,
TR-09).

**Explicitly rejected framing:** an "express service" that labels
items on arrival. Event-driven labeling needs a webhook endpoint, an
App identity, and autonomous writes — that is the M4 service spike
(design v0.6 §12), which is research-only behind hardened go/no-go
criteria precisely because of the standing attack surface. "At the
start, once an item arrives" translates in this architecture to a
cheap command the maintainer runs, not a daemon. Nothing below
prejudges M4; if M4 ever goes, the label skill's rules are what the
service would enforce.

## Feature 1 — Label support: a fifth skill plus a sync obligation

### The gap

The agent classifies every item (lane, category, tier, issue class,
outcome) but none of that state is visible on the GitHub item itself.
A maintainer scanning the queue in the GitHub UI — or a contributor
wondering what happened to their PR — sees nothing until a comment is
posted. Labels are the native GitHub surface for exactly this, and
they are cheap, reversible writes.

### The shape

**A new skill, `/lq-maintainer:label`** — the express first touch.
Deliberately lighter than triage: no deck, no receipt, no digest, no
merge-order computation. It fetches the item(s), makes a
**provisional** classification from the same rule files the router
uses (`rules/lanes.md`, `rules/change-categories.md`,
`rules/issues.md` — never a fork of them), maps the result through the
taxonomy (below), and offers the label writes **one at a time**, each
behind its own permission prompt, exactly like every other write.
Modes:

- `/lq-maintainer:label pr N` / `issue N` — one item, on arrival.
- `/lq-maintainer:label` — sweep open items whose agent-managed
  labels are missing or stale.

**Why not fold this into triage:** triage loads eleven rule files,
renders a deck per item, and computes queue groups — it is the
30-minute-session tool. The labeler wants to be seconds-cheap and
runnable the moment something arrives. Different weight class,
different command. The cost of a second entry point is divergence
risk, which the sync obligation pays down:

**The sync obligation.** Triage and both review skills, on their
fuller pass, diff the item's current agent-managed labels against the
settled classification and offer corrections as gated writes. The
internal receipt is the authority; labels are its cheap public
shadow, and the deeper pass always wins. A label applied by
`/lq-maintainer:label` is provisional by construction and says so
nowhere on GitHub — it just gets corrected quietly when the fuller
pass runs.

### The rules file — `rules/labels.md` (LB-NN)

- **LB-01 — Labels are outputs only, never inputs.** The existing
  invariant, promoted to its own rule: no lane, category, tier,
  queue-group, or anchor determination ever reads a label
  (`rules/queue.md` Q-01, `rules/anchoring.md`, and
  `rules/change-categories.md` already say this item-by-item). Label
  support makes labels a *projection* of agent state; nothing changes
  on the input side, including for the agent's own labels — resume
  reads the receipt footer, never the label set.
- **LB-02 — The mapping (ruled 2026-08-05): the target repo's own
  taxonomy, never an invented one.** The agent maps its
  classifications onto labels that already exist in the target repo —
  it never creates a label and never introduces agent-specific
  vocabulary (`cat:*` schemes are rejected). The mapping table lives
  in `rules/labels.md` as target-repo vocabulary — the same portable
  seam as `rules/canon-map.md`; another project rewrites the table.
  Against lq-ai's actual label set (fetched 2026-08-05):
  - category → `bug` (G bug-fix/rollback) and `enhancement`
    (G greenfield *and* behavioral — lq-ai draws no finer line, so
    neither does the projection); refactor/large-scale has no lq-ai
    label and projects nothing;
  - the detector's flag → `breaking-change` (exists in lq-ai;
    Feature 2);
  - issue recommendation → `question` (lq-ai's "further information
    is requested" *is* needs-info) and `duplicate` (from the agent's
    own C-60 cross-reference, never the filer's claim);
  - lane/paths → `documentation` (docs lane), `dependencies`
    (dependency items);
  - **component labels from changed paths** — `api` / `gateway` /
    `web` / `ci`, assigned mechanically from the diff's paths via the
    component map in `rules/labels.md` (path prefixes verified
    against the clone at the pinned canon SHA). Deterministic,
    contributor-useful, and impossible to get from the narrative.
- **LB-02a — Runtime existence check.** The mapping is validated
  against `gh label list` output each run: a mapped label missing
  from the target repo is *reported*, never created — the taxonomy is
  the target repo's to change (ruled 2026-08-05).
- **LB-03 — What never becomes a label.** Lanes and tiers are
  internal routing vocabulary — `escalate` on a public PR is at best
  alarming and at worst a signal to an attacker that they tripped a
  wire. **The §8.3 carve-outs bind labels as public output:** an item
  under E-21 (suspected deliberate attack) gets no label change at
  all until the maintainer rules, and a vulnerability-suspect issue
  gets no label, period — the private-advisory redirect stays the
  only output (C-40). In particular the agent **never drafts lq-ai's
  `security` label**: on the one class of item where it would be
  accurate, applying it is exactly the public disclosure the
  carve-out forbids, and a label that is safe only when it is wrong
  is not worth drafting. Judgment labels stay human-only too —
  `invalid`, `wontfix`, `good first issue`, `help wanted` are
  maintainer rulings and invitations, not classifications. Burden
  axes, findings, and confidence values never label.
- **LB-04 — Stale labels are corrected, not layered.** The sync pass
  removes an agent-managed label the settled state contradicts in the
  same gated write that adds the replacement; agent-managed labels
  are exactly the LB-02 set, and the agent never touches a label
  outside it (maintainer-applied labels like `frozen`/`no-stale` are
  someone else's writes — the stale sweep already honors them as
  input it never modifies).
- **LB-05 — No label creation, ever.** Superseded by LB-02a (ruled
  2026-08-05): the taxonomy is the target repo's own; the agent maps
  onto what exists and reports what does not. If lq-ai wants a new
  label, that is an lq-ai decision made by its maintainers in its
  repo — the agent-side change is one row in `rules/labels.md`.

### Receipt/footer delta

The `receipt:v2` footer gains one optional enumerated field:
`labels_synced: [<name>, …]` — the agent-managed label set as of the
last sync, so the next session can diff without refetching label
history. Additive, same backward-compatibility posture as the v0.7.1
`decision_scoping` block.

## Feature 2 — Breaking-change detection: a rule + script, not a command

### The gap

`rules/reversibility.md` RV-02 already names **public API contracts**
as an irreversible class that blocks Tier 1 — but nothing *detects*
the class mechanically; it rides on the model noticing. The other
irreversible classes have cheap structural detectors (paths for
CI/workflow files, manifests for new dependencies). Public-API breaks
deserve the same deterministic-first treatment as the dependency
gate: scripts decide what scripts can decide; the model judges what
they cannot see.

### The shape

**A check script, `skills/triage/scripts/check-breaking.sh`** (same
polyglot pattern, machine-parseable PASS/FAIL with an evidence line
per finding), run over the diff of every standard-lane PR at Step 6b
and by `review-pr`. Detects, from the diff only:

- removed or renamed exported/public symbols, and public signature
  changes (parameter removal/reorder, return-type change);
- removed or renamed config keys, environment variables, and CLI
  flags;
- removed/renamed HTTP routes or changed response contracts where the
  target repo's structure makes them textually visible;
- schema/migration files that drop or narrow columns (already
  RV-02's data class — the script cites both).

**A small rules file, `rules/breaking-changes.md` (BC-NN)**, defining
what each detection means and the honesty bounds:

- **BC-01** — a detection fires the RV-02 public-API irreversible
  class: Tier 1 ineligible, the entering condition named on the card
  (`rules/tiers.md` TR-07), the `breaking-change` label drafted
  (LB-02).
- **BC-02** — the model layers judgment *on top of* the script, never
  instead of it: semantic breaks the script cannot see (behavioral
  contract changes under an unchanged signature) are findings with
  the v0.7.1 impact/ask/scope fields, and they fire BC-01 the same
  way.
- **BC-03 — absence of detection proves nothing.** A PASS means "no
  textual break detected", never "non-breaking". The coverage
  statement gains a standing line for category-2/3 items: breaking
  detection is heuristic and diff-textual; runtime behavior is never
  checked. The detector can only ever move an item heavier (TR-09) —
  a PASS never overrides a fired trigger, a maintainer's call, or
  any other irreversible-class hit.
- **BC-04** — dependency-bump majors are already the semver script's
  job; `check-breaking.sh` does not re-derive them (no overlap, one
  authority per check).

### Why not a skill

There is no user act here — nobody "runs breaking-change detection";
they triage or review, and the detection is evidence inside those
passes. A command would just be `review-pr` with fewer steps.

## Feature 3 — The release narrative: a sixth skill

### The gap

When a maintainer cuts a target-repo release, the narrative is
assembled by hand from merged PRs — exactly the attention-routing
problem this agent exists for, and the one moment where the agent's
accumulated evidence (categories, outcomes, breaking flags, merge
trailers) pays off across items instead of per item.

### The shape

**A new skill, `/lq-maintainer:release-notes [<ref>..<ref>]`** —
defaults to last-tag..HEAD in the clone. Read-only inputs:

- `git log` over the range in the clone (the merge trailers carry the
  four pinned fields per §8.5, so every squash-merged item is
  traceable to its review);
- `gh` reads for the merged PR list and linked issues;
- the internal evidence store: each item's receipt footer supplies
  category, outcome, undo class, `labels_synced`, and any BC-01
  flag — enumerated fields only, which is exactly what a narrative
  needs;
- the target repo's own changelog/release conventions via
  `rules/canon-map.md` (new key `canon:release-conventions`, added
  only if the target doc resolves at the pin — else the template's
  default structure applies and the draft says so).

Output is rendered from a new **`templates/release-notes.md`
(RN-NN)** — render, never freehand:

- **Breaking changes lead** (the security-first ordering instinct the
  digest already has), each with its undo/migration line (RV-05 is
  already per-item state). lq-ai's own `breaking-change` label
  description already promises this contract — "If this issue or PR
  is resolved, you should read the release notes" — so the label the
  detector drafts (Feature 2 via LB-02) is the exact query this
  section is built from;
- then grouped by category: features (with their design-path
  provenance where one exists), fixes, everything else;
- **contributor credit per item** (CD-NN binds the voice; the squash
  attribution work in v0.7.1 §4 means the trailer data is already
  clean);
- a provenance block: the range, canon SHA, agent version, served
  model ID — the pinned-fields discipline applied to the one artifact
  that spans items.

**Injection posture applies with full force:** PR titles and bodies
quoted into a release narrative are contributor text flowing into a
*published* artifact — normalized before judging, quoted as data,
never as instructions; a reviewer-directed span found in a title is a
finding, not copy. The narrative is contributor-facing public output,
so the **tone gate runs on the whole draft** and the attribution line
rides it like every public artifact.

**The human publishes.** The skill drafts the narrative (and, where
asked, the `gh release create` invocation) — each write gated;
tagging is a push, which stays hook-blocked, so the tag is always the
maintainer's own act. **A semver suggestion is drafted, never
decided:** any BC-01 item in the range ⇒ suggest major; otherwise
features ⇒ minor, fixes-only ⇒ patch — stated with the evidence
lines, decided by the human.

## Sequencing

1. **Feature 2 first** — smallest, no new skill, and both other
   features consume its flag.
2. **Feature 1 second** — wants `breaking-change` in the taxonomy
   from day one.
3. **Feature 3 third** — consumes both, plus the trailer/receipt
   plumbing that already shipped in v0.7.1.

Each lands with its eval fixtures (a BC-positive and BC-negative PR
fixture; a label-sync golden asserting LB-03's carve-out — an E-21
fixture whose expected label delta is *empty*; a release-notes golden
over a synthetic range with one breaking item).

## Rulings (2026-08-05)

The proposal's three open questions were put to the maintainer and
ruled as follows; the body above is updated to match.

1. **Taxonomy: the target repo's own.** lq-ai already has a label
   taxonomy — the agent uses it. No invented vocabulary, no `cat:*`
   scheme, no label creation; the agent-side artifact is the mapping
   table in `rules/labels.md` (LB-02/LB-02a), and a missing label is
   reported, never created.
2. **Release-notes target: lq-ai, or a repo like it — never this
   repo.** The skill serves the *target* repository and runs inside
   its clone like every other skill; the Step-0 repository-identity
   check applies unchanged, so pointing it at this repo fails by
   design. No escape hatch. This repo's own release narrative stays
   a manual act (today's transcript-mining practice).
3. **Label colors/descriptions** — mooted by ruling 1: the labels
   already exist in lq-ai with their colors and descriptions; the
   agent changes none of them.
